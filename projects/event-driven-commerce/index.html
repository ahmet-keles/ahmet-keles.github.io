The problem I set myself

I wanted to build the part of a commerce backend that is genuinely hard: not the CRUD, but the coordination. Placing an order touches three different concerns, orders, stock, and money, and each one has its own rules about what can go wrong. The naive design is one service with one database and a big transaction. That works right up until you need the pieces to scale, fail, or deploy independently.

So I set three constraints before writing any code:

  • No synchronous calls between services. Every hop goes through Kafka. If a service is down, work queues; it does not fail.
  • No shared database. Each service owns its schema. The only integration point is the event contract.
  • Every guarantee has to be tested against the real thing. No mocked Kafka, no in-memory database. If the claim is "a duplicate delivery never double-charges", there is a test that delivers a duplicate to a real broker and checks the payment table.

The result is a system where at-least-once delivery, retries, redelivery, and concurrent writers are all assumed to happen, and the correctness comes from making every effect idempotent rather than hoping nothing goes wrong.

Architecture

Every hop uses the same mechanism. A business transaction writes its domain change and an outbox row in one database transaction. A scheduled publisher later ships unpublished rows to Kafka. On the other side, every consumer records the event id in a processed_events ledger inside the same transaction as its mutation. That pairing, outbox on the way out and ledger on the way in, is what turns at-least-once delivery into effectively-once effects.

The saga

create order ──▶ add items ──▶ submit
                                 │
              ORDER_ITEM_ADDED   ▼            per item
order-service ────────────────▶ inventory-service ──▶ INVENTORY_RESERVED
                                                  └─▶ INVENTORY_RESERVATION_FAILED
submitted AND all items reserved ⇒ CONFIRMED ── ORDER_CONFIRMED ──▶ payment-service
any reservation failure          ⇒ CANCELLED                            │
                                                    PAYMENT_COMPLETED ◀─┴─▶ PAYMENT_FAILED
                                                    (order settles)          (order CANCELLED,
                                                                             stock released)

The client assembles an order item by item, then explicitly submits it. Each item added produces an ORDER_ITEM_ADDED event that inventory-service reserves against. The order confirms only when it has been submitted and every item is reserved, whichever happens last. Confirmation emits ORDER_CONFIRMED, which payment-service charges. A declined charge cancels the order, and the cancellation event makes inventory-service return every reservation it still holds. Every cancellation compensates, exactly once.

Decisions and tradeoffs

Transactional outbox instead of publishing from the business transaction

Calling kafkaTemplate.send() inside a service method is the obvious approach and it is wrong in both directions: a commit can succeed after the send fails (state with no event), or the send can succeed and the commit roll back (event for state that never existed). The outbox makes the event part of the same atomic write. The cost is a polling publisher and a one-second delay. I also considered change data capture with Debezium, which avoids polling, but it adds a connector to operate and I wanted the guarantee to be visible in the code I wrote.

The publisher has to survive running twice

The first version claimed rows with a plain SELECT. Two replicas would have published the same rows. The fix is SELECT … FOR UPDATE SKIP LOCKED inside one short transaction, so concurrent replicas partition the backlog instead of racing for it. A second guard checks, inside the claim transaction, that this replica holds the aggregate's oldest unpublished event. Without that, two replicas could publish one order's INVENTORY_RESERVED and INVENTORY_RESERVATION_FAILED in the wrong order and flip its terminal state. The guard costs one indexed query per poll and can only defer, never publish early.

Explicit submission

Originally an order confirmed as soon as its items were reserved. That meant a fast reservation could confirm an order the client was still adding items to. Adding a submit step makes "assembly is finished" a fact the client states rather than something the system infers from timing. It is one more API call, and it removed an entire class of race.

Optimistic locking, with Kafka owning the retry

The order aggregate and inventory rows carry a JPA @Version. Concurrent writers, an addItem racing a reservation, a reservation racing a cancellation, serialize into exactly one committed ordering. I deliberately put no retry loops in the service layer. A losing transaction rolls back, including its ledger claim and its outbox row, and the Kafka error handler redelivers. REST callers get a 409 concurrent_modification whose contract is "retry". One retry mechanism instead of two.

Classify failures before deciding how to handle them

ClassExampleHandling
Business outcomeinsufficient stock, declined chargeCommit and emit a failure event. Never a retry, never a dead letter.
Contract violationmissing event id, envelope/payload mismatchStraight to <topic>.DLT. Retrying cannot fix a malformed record.
Transientlock conflict, connection lossExponential backoff, 4 attempts, 500 ms → 5 s, then DLT.
Duplicateredelivered event idDropped by the ledger. Consumed successfully.

The important line is the first one. "Not enough stock" is not an error. Treating it as one would retry a hopeless operation four times and then dead-letter a perfectly good message.

The ledger claim lives inside the mutation's transaction

It is tempting to record "I processed this event" in its own REQUIRES_NEW transaction so it survives whatever happens next. That is exactly backwards: if the mutation then fails, the marker is committed and the event is lost forever. The claim is an INSERT … ON CONFLICT DO NOTHING in the same transaction as the work, so a rollback releases it for the redelivery to take.

Charge at most once, three layers deep

Payment gets three independent guards because it is the one place where a duplicate costs real money: the ledger dedups a redelivered event id, a unique constraint on payments.order_id absorbs a confirmation re-emitted under a fresh id, and the gateway idempotency key is the order id itself, so a crash between charge and commit replays into the original outcome. The gateway is simulated and deterministic, amounts under 1000.00 approve, at or above decline, which is enough to exercise both branches end to end.

What broke along the way

These are real bugs from the commit history, not hypotheticals. Each one now has a test that would catch it again.

  • The first reservation confirmed the whole order. The consumer called confirmOrder() unconditionally on the first INVENTORY_RESERVED, so a two-item order confirmed before its second item was even checked. Fix: track a reserved flag per item and derive confirmation from the items. A flag rather than a counter, so a redelivered event for an already-reserved item cannot advance the order.

  • Cancelling an order did not give the stock back. The happy path worked and the compensation was simply missing. Fixing it needed a durable reservation ledger in inventory-service keyed by order item, and a per-order state row that both reserve and release lock first, so a late ORDER_ITEM_ADDED arriving after the cancellation reserves nothing instead of leaking stock.

  • The outbox publisher could hold locks for 1000 seconds. After making it replica-safe, the claim transaction ran until every send resolved: batch size × send timeout. A degraded broker would have pinned row locks and a pooled connection for the duration. The hold is now capped three ways, a poll deadline, a local send timeout that aborts the rest of the poll, and a lowered max.block.ms, so the worst case is 8 seconds regardless of batch size.

  • A fresh consumer group silently skipped events. order-service relied on Kafka's default auto-offset-reset=latest. A new consumer group would ignore inventory and payment events published before its first assignment, leaving orders unconfirmed. The end-to-end suite had an environment override that masked this. Both were fixed and a config test now pins earliest.

  • The dedup window was shorter than the replay window. The ledger's retention default was 7 days. Deleting a ledger row re-enables its event id, so the retention has to exceed Kafka's topic retention plus any dead-letter redrive window. It is now 30 days, and the configuration refuses to boot on a non-positive age.

  • The e2e suite failed intermittently on a real race. POST /items races the Kafka consumer's writes to the same order row. The suite was hitting the genuine 409 the service now returns. The fix was not to loosen the test but to make the test client honor the 409's contract with a bounded retry, while never retrying the terminal order_not_modifiable.

The tests I am most pleased with are the concurrency proofs. They use latches to force a specific interleaving, for example a cancellation that stages CANCELLED plus its outbox row and parks before commit, while a reservation commits first and confirms the order. The released cancellation must then fail its version check and leave zero ORDER_CANCELLED rows behind. A surviving row would announce a cancellation that never happened and make inventory release stock for a confirmed order.

The end-to-end suite covers the full saga, compensation, duplicate delivery, dead-lettering in both directions, both payment outcomes, and the wire contracts. All four suites run in GitHub Actions on every push and pull request.

What I would do differently

  • Add the submit step on day one. Inferring "assembly finished" from event timing was the root of two separate bugs. State that the client knows should be stated by the client.
  • Write the compensation path with the happy path. Reservation without release shipped and passed its tests. A saga is not done until every forward step has its undo.
  • Test every consumer against a fresh consumer group. The offset-reset bug survived because the test environment configured what the application did not. Tests should run the real defaults.
  • Use a schema registry or at least versioned contracts. Payloads are JSON strings inside a JSON envelope with the field names checked by tests. That works for three services I control. It would not survive a fourth team.
  • Add metrics before adding services. Outbox backlog depth, consumer lag, and DLT counts are the three numbers an operator would need, and today they only exist in logs.

Status and next steps

v1.0.0 is complete: the saga runs end to end, and every guarantee above is pinned by a test. Local deployment is hybrid, Docker Compose runs Kafka, the three databases, and payment-service, while the other two services run on the host. Natural next steps are a notification service, metrics and tracing beyond Actuator health, and a cloud deployment.

Read the code. The repository's ARCHITECTURE.md and EVENT_FLOW.md document every contract and mechanism in more detail than this page. Two of the mechanisms have their own write-ups: the transactional outbox and idempotent consumers.
