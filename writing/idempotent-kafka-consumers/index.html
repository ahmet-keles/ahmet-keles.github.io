Idempotent Kafka consumers: the claim goes inside the transaction

At-least-once delivery means every consumer will eventually see the same event twice. A ledger of processed event ids handles that. Where you write to the ledger decides whether a retry can lose the event forever.

September 18, 2026 Java · Spring Kafka · PostgreSQL

Duplicates are not a bug, they are the contract

In the previous post I described an outbox publisher that is deliberately at-least-once. A send that succeeds before a commit that fails gets re-sent. A send that times out locally but lands at the broker gets re-sent. Kafka itself redelivers on consumer rebalance and on any retry the error handler schedules. So every consumer in the system has to be written on the assumption that it will see any given event more than once, and the effect must happen exactly once anyway.

The ledger

Each service has a processed_events table keyed by the envelope's eventId. Before applying an event, the consumer tries to claim it: 

INSERT INTO processed_events (event_id, event_type, aggregate_id, processed_at)
VALUES (:eventId, :eventType, :aggregateId, :processedAt)
ON CONFLICT (event_id) DO NOTHING

The insert is the duplicate check. There is no window between looking and writing, because the primary key arbitrates. If the row count comes back 0, a committed delivery already handled this event, and the consumer returns without doing anything. When two transactions race on the same id, PostgreSQL blocks the second insert until the first resolves, so 0 is only ever returned after a competing claim has committed. An aborted competitor lets this insert proceed. No exception is thrown either way, so the surrounding transaction stays usable. 

@Transactional
public boolean processReserved(Envelope envelope, InventoryReservedEvent event) {
    int claimed = ledger.claim(envelope.eventId(), envelope.eventType(),
                               envelope.aggregateId(), Instant.now());
    if (claimed == 0) {
        return false;                 // already applied by an earlier delivery
    }
    orderService.markItemReserved(event.orderId(), event.orderItemId());
    return true;
}

The mistake that looks like defensive programming

The tempting refinement is to commit the ledger write in its own transaction, REQUIRES_NEW, so the marker survives whatever happens next. It reads as extra safety. It is the opposite.

Suppose the claim commits on its own, then the mutation throws: an optimistic-lock conflict, a flush error, a constraint. The mutation rolls back. The claim does not. The error handler redelivers the event, the consumer sees the ledger row, returns "already processed", and the effect never happens. The event is lost, permanently, with a log line that says everything is fine.

So the claim and the mutation share one transaction. If anything after the claim fails, the claim rolls back with it, and the redelivery can claim the same id again. This also composes with optimistic locking: a consumer that loses a version race rolls back its claim, its mutation, and any outbox row it staged, and the retry re-applies cleanly from the fresh state.

Let the domain be defensive too

The ledger is the general guarantee, but a few places get a second guard because the cost of a duplicate is high or because the ledger's window is finite:

  • Per-item reserved flags on the order, not a counter. A redelivered INVENTORY_RESERVED for an item that is already reserved cannot advance the order, even when two items share a product.
  • Terminal states latch. A late reservation cannot confirm a cancelled order; a late failure cannot cancel a confirmed one. The first terminal payment outcome wins.
  • A unique constraint on payments.order_id, and the payment gateway idempotency key is the order id. Even a confirmation re-emitted under a brand new event id, which the ledger would not catch, cannot charge twice.

Classify the failure before choosing the retry

Idempotency makes retries safe. It does not make them useful. Every listener in the system shares one DefaultErrorHandler with exponential backoff (4 attempts, 500 ms doubling to 5 s) and a DeadLetterPublishingRecoverer that publishes exhausted records, unchanged and under their original key, to <topic>.DLT. What matters is which exceptions get which treatment: 

errorHandler.addNotRetryableExceptions(
        InvalidEventException.class,          // contract violation: retrying cannot fix it
        DataIntegrityViolationException.class // a broken record breaks the same constraint every time
);
errorHandler.addRetryableExceptions(
        TransientDataAccessException.class,   // lock conflicts, deadlocks, connection loss
        DuplicateKeyException.class           // a racing duplicate insert resolves on redelivery
);

And the category that is not an exception at all:

ClassExamplesHandling
Business outcomeinsufficient stock, unknown product, declined chargeCommit, emit a failure event. Never retried, never dead-lettered.
Contract violationmissing event id, envelope/payload order id mismatchStraight to the DLT. The partition keeps moving.
Transientoptimistic-lock loss, lock timeoutBackoff and retry. The rolled-back claim lets the retry apply cleanly.
Duplicateredelivered event idClaim returns 0. Consumed successfully.

The first row is the one people get wrong. "Not enough stock" is a perfectly valid answer to a reservation request. If the consumer throws on it, the error handler retries a hopeless operation four times and then dead-letters a good message. Model it as INVENTORY_RESERVATION_FAILED instead, commit it, and let the order service decide what to do.

The ledger has a retention window, and it bounds the guarantee

Ledger rows cannot live forever, so a retention job deletes them after a configured age. Deleting a row re-enables its event id. That means the ledger age must exceed the source topic's retention plus the worst-case consumer lag plus any operational replay or dead-letter redrive window. My first default was 7 days, which is shorter than a plausible redrive. It is now 30 days, the property is documented with the constraint, and a non-positive value refuses to boot. Past the window, the domain guards above still prevent double stock mutation and double charging, but the general promise is gone.

One more thing: the offset reset

None of this helps if the consumer never sees the event. Kafka's default auto-offset-reset is latest, so a brand new consumer group starts from the end of the topic and silently skips everything published before its first partition assignment. I relied on that default in one service and only found it because the end-to-end suite had an environment override masking it. All three consumers now set earliest, and a config test pins it. Test your real defaults, not the ones your test harness sets for you.
