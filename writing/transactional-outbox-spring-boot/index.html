A transactional outbox that survives two replicas

Publishing Kafka events from inside a database transaction is wrong in both directions. The outbox pattern fixes that. But the first outbox I wrote broke the moment two copies of the service polled the same table.

September 18, 2026 Java · Spring Boot · PostgreSQL · Kafka

Why not just call send()?

The obvious way to emit an event is to call kafkaTemplate.send() from inside the service method that changes state. It fails two ways:

  • The send succeeds, then the transaction rolls back. Kafka now carries an event describing state that never existed.
  • The transaction commits, then the send fails. The state changed and nobody will ever hear about it.

The transactional outbox closes both gaps by making the event part of the same atomic write. The service inserts an outbox_events row in the same transaction as the domain change. A separate publisher polls for unpublished rows and ships them to Kafka. If the business transaction fails, the row never exists. If the send fails, the row stays and is retried. 

outbox_events
  id             uuid primary key   -- becomes the envelope's eventId
  aggregate_type text               -- "Order"
  aggregate_id   uuid               -- also the Kafka message key
  event_type     text
  payload        text               -- JSON, serialized before storing
  occurred_at    timestamptz
  published_at   timestamptz null   -- stamped only after broker ack

Version one: a SELECT and a loop

My first publisher was about what you would expect:

@Scheduled(fixedDelay = 1000)
public void publish() {
    for (OutboxEvent e : repo.findTop100ByPublishedAtIsNullOrderByOccurredAtAsc()) {
        try {
            kafka.send(topic, e.getAggregateId().toString(), toJson(e)).get();
            e.markPublished();
            repo.save(e);
        } catch (Exception ex) {
            log.error("failed, will retry", ex);
        }
    }
}

It worked with one instance. It has two bugs that only show up with two.

Both replicas claim the same rows. There is no transaction around the read, so two pollers see the same 100 unpublished rows and both publish them. Consumers deduplicate on event id, so nothing corrupts, but every event is sent twice and the two instances fight over published_at.

A failed send reorders the aggregate. The per-event catch skips the failed row and carries on. If event 3 for an order fails and event 4 succeeds, Kafka receives 4 before 3. My consumers are not reorder-tolerant: INVENTORY_RESERVED and INVENTORY_RESERVATION_FAILED drive first-writer-wins transitions, so inverting them flips an order's terminal state.

Version two: claim with SKIP LOCKED

PostgreSQL has exactly the primitive this needs. Claim the batch inside a transaction with FOR UPDATE SKIP LOCKED. Rows another replica is holding are skipped rather than waited on, so concurrent pollers partition the backlog between themselves. 

SELECT *
FROM outbox_events
WHERE published_at IS NULL
ORDER BY occurred_at ASC, id ASC
LIMIT :batchSize
FOR UPDATE SKIP LOCKED

The locks live exactly as long as the claiming transaction, so I mark the repository method @Transactional(propagation = MANDATORY). A caller without a transaction would silently release each lock at statement end and defeat the whole point, so it fails fast instead. A replica that crashes mid-batch loses its connection, its locks go with it, and the rows it never published reappear for the next poller.

Inside the batch, a failed send now blocks the rest of that aggregate's events for the remainder of the poll. Other aggregates continue, so one poisonous row cannot stall the whole outbox.

Version three: the lock hold I did not think about

Review of version two found a problem I had not considered. The claim transaction ran until every claimed send resolved. With a batch of 500 and a send timeout of 2 seconds, a degraded broker could hold row locks and a pooled connection for 1000 seconds. That is not a theoretical number, it was the product of my own defaults.

The hold is now capped three ways, none of which depend on batch size:

  1. A poll deadline (4 s). No new send starts after it. Unreached rows stay pending for the next poll.
  2. A local send timeout (2 s) that aborts the rest of the poll. A local timeout means the broker is degraded, and spending a timeout per remaining row would multiply the hold for no benefit.
  3. Producer max.block.ms configured down to 2 s, so a metadata stall inside send() cannot pin the transaction for the producer default of 60 seconds.

Worst case is deadline + max.block + send-timeout = 8 seconds, on one connection per replica. I reduced the batch to 25 as well, but the bound no longer relies on that.

Ordering across replicas

SKIP LOCKED introduces a subtler reordering. Replica A claims an order's event 3. Replica B polls, skips the locked row, and claims event 4 of the same order. B publishes 4 before A publishes 3. Same-key-same-partition does not help because the events arrive at the broker out of order.

The fix is a check inside the claim transaction: for every aggregate in my batch, am I holding its oldest unpublished event? 

SELECT DISTINCT ON (aggregate_id) id
FROM outbox_events
WHERE published_at IS NULL
  AND aggregate_id IN (:aggregateIds)
ORDER BY aggregate_id, occurred_at ASC, id ASC

If the oldest pending id for an aggregate is not the first one I claimed, another replica has the earlier event in flight, so I defer that aggregate to a later poll. Under READ COMMITTED a row the other replica already committed as published is invisible here, and a row it failed on still counts as pending. Both cases make the guard conservative: it can only defer needlessly, never publish early. It costs one indexed query per poll and needs no schema change.

What this does and does not give you

Delivery is at-least-once, not exactly-once. published_at is stamped only after the broker acknowledges the send, never before, so a failure between send and commit re-sends rather than loses. Two windows produce duplicates on purpose: the send succeeds but the commit fails, and the send times out locally but the broker accepts it anyway. Consumers must deduplicate on event id. That is the subject of the next post.

Per-aggregate ordering is preserved end to end. Cross-aggregate ordering is not, and should not be relied on.

Testing it

Every property above has a Testcontainers test against real PostgreSQL: concurrent claims never overlap, locked rows are skipped rather than waited on, two publishers send each event exactly once, failed and timed-out sends leave rows pending, a later event is held while another transaction locks the earlier one and is published in order once released, and an expired poll deadline sends nothing and leaves every claimed row claimable. I would not trust a locking contract I had only reasoned about.
